# Разбор: как делал

## Инструменты и порядок

Работал в Claude Code (десктоп-приложение), модель Claude Sonnet 5.5. Порядок:

1. **Разбор задания и границы.** Выписал обязательное (бот → лид с тегом, ручной ввод, теги) и необязательное (обычный Telegram). Решил делать все четыре пункта, но пункт 2 через официальный Telegram Business, а не юзербот, потому что он не требует хранить сессию аккаунта и не рискует баном.
2. **Стек под «живую ссылку».** Python без зависимостей + SQLite + один HTML: деплой это копирование папки и systemd-юнит, ломаться нечему. Бот на long polling, чтобы не зависеть от домена и сертификата.
3. **Данные и бот первыми** (`db.py`, `bot.py`), интерфейс потом. Сначала схема лидов/тегов/диалогов и логика диалога, потому что на них держится сквозной сценарий.
4. **API и интерфейс** (`server.py`, `static/`): список, фильтр по тегу в адресной строке, карточка лида, окно с инструкцией подключения Telegram.
5. **Проверка трёх уровней.** Юнит-тесты на диалог и API (на первой итерации 17, после расширения, ревью и сверки с ТЗ 86). Затем сквозной прогон: фальшивый Telegram API на localhost, настоящий поллер, сообщения боту → лид с тегом, `business_message` → лид с тегом. Затем руками в браузере: вход, ручной лид с двумя тегами, фильтр по тегу.

## Что делали ИИ-инструменты и что нашла проверка

- Claude Code написал код по моему заданию, прогонял тесты и браузер, чинил найденное.
- Реальная ошибка, найденная тестами: поиск «мар» не находил «Мария» — `LIKE` в SQLite нечувствителен к регистру только для латиницы. Исправлено своей функцией `ulower`; та же причина у `COLLATE NOCASE` на тегах («Срочно» и «срочно» были бы разными тегами), там тоже исправлено, в тесте это закреплено.
- На настоящем Telegram проверено: подключение бота и сценарий «сообщение боту → лид с тегом» на живом сервере через прокси. Не проверено вживую: ответы клиенту из CRM, уведомления менеджеру и Business (нужен Premium), они гонялись на эмуляторе, а формат апдейтов взят из документации Bot API.

## Вторая итерация

После работающего ядра расширил продукт: ответы клиенту из CRM, доска, ответственные, сроки и суммы, автотеги, метки в ссылке на бота, публичная форма, уведомления менеджеру, импорт/экспорт CSV, сводка, история изменений. Дизайн переделал отдельно: шрифт Unbounded, бумажная палитра с одним акцентом, без градиентов, теней и скруглённых карточек, светлая и тёмная тема. Интерфейс проверял в браузере на десктопе и в мобильной ширине, нашёл и поправил переполнение таблицы, растянутый счётчик, обрезанные селекты и горизонтальную прокрутку на телефоне.

## Ревью и баги

Отдельным проходом перечитал весь код и для каждой находки сначала написал тест, который падает, и только потом чинил. Самое существенное:

- **Бот крутился вхолостую.** Параметр `timeout` длинного опроса уходил в сокет, а Telegram его не получал и отвечал мгновенно. Эмулятор с задержкой маскировал проблему. Теперь таймаут уходит в Telegram, а у сокета запас.
- **Пароль с кириллицей не работал** (`compare_digest` падал на не-ASCII), то же с кодом `/connect`.
- **Лимиты за reverse proxy были общими на всех:** все запросы приходили с 127.0.0.1, форму после пяти заявок блокировало для всех посетителей. Теперь берётся правый адрес из `X-Forwarded-For`, левые клиент подделать не может.
- **Зависание на `Content-Length: -1`** и отсутствие таймаута сокета (медленный клиент держал поток вечно).
- **Старая сессия оставалась рабочей после смены пароля.**
- **Владелец Business-аккаунта становился лидом,** если апдейт подключения пришёл до запуска бота.
- **После ответа клиенту форма карточки возвращала статус «Новый»** при сохранении.
- **Экспорт обрезался на 1000 лидах**, CSV из Excel (cp1251) импортировался кракозябрами, очень длинный id в адресе давал 500, срок в формате «20261005» проходил валидацию и ломал сравнения.
- Поменьше: кнопка «Сбросить» не появлялась при наборе в поиске, свой же лид давал тост «новый лид», открытая карточка оставалась поверх экрана входа, правила автотегов воскрешали переименованный тег, две правки в одну секунду не обновляли другую вкладку, брошенный диалог бота принимал запрос за имя через неделю.

Скриншоты для README ещё раз показали три дефекта, которых не видели ни тесты, ни беглый просмотр: слово «null» над таблицей лидов (моя же правка из ревью), мелкие суммы в плитках сводки и плитки в одну колонку на телефоне. После этого добавил дымовой тест интерфейса, который находит первое из них.

Дополнительно прогнал фаззинг по всем эндпоинтам: странные типы, нулевые байты, гигантские значения, битый JSON и CSV. Он нашёл баг с огромным id, остальное устояло.
